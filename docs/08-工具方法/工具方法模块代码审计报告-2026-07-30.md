## 4. 各维度详细发现

### 4.1 代码质量
- ✅ 命名规范统一：`calc_*`（测算）/ `assess_*`（判定预警）/ `build_*`（结构化结果），与 `__init__` 约定的封装接口规范一致。
- ✅ 单一职责：每个函数只做一件事，无超长函数（最长 `calc_tax_adjustment` 约 90 行，但为线性累加，可理解）。
- ⚠️ 重复代码（F-11）：三个 Altman 变体除系数外逻辑一致，可收敛为带权重表的函数。
- ⚠️ 代码异味（F-10）：`scan_invoice_risk` 冗余三元，功能正确但应清理。

### 4.2 安全性
- ✅ 无注入/越界风险：纯算术，无 `eval/exec`、无文件/网络/子进程，无密钥。
- ✅ 输入校验：基础层 `require_number/non_negative/positive/in_range` + `ToolValidationError` 覆盖大部分入口；业务预警写入 `warnings` 不中断。
- ⚠️ 校验缺口（F-02）：`tax_health_score` 入参为字符串等级，未做白名单校验，错误输入被静默忽略——属"输入信任"类安全隐患，上线一线工具前必须封堵。

### 4.3 性能
- ✅ 无性能问题：`DCF` 仅对预测期列表做一次 O(n) 遍历；其余均为常数级；无循环内重复校验或冗余对象分配；无外部资源（文件/网络/DB）。
- 备注：各函数 `round()` 后返回，未做大规模批处理，当前规模无优化必要。

### 4.4 可维护性
- ✅ 低耦合达成：各方法模块仅依赖 `base`，互相不引用；统一 `ToolResult` 返回结构，便于后续封装为独立模块 / WorkBuddy Skill。
- ⚠️ 缺类型注解（F-06）：影响静态检查与调用方提示。
- ⚠️ 缺测试套件（F-08）：当前无纳入版本库的回归测试，重构时易回归。
- ⚠️ 魔法数字（F-07）：阈值散落，调参/评审成本高。
- ⚠️ 文档不一致（F-04、F-05）：包示例包名错、F 分数阈值注释与默认参数矛盾。

### 4.5 边界条件处理
- ✅ 大部分边界已覆盖：零/负/除零（`require_*`）、权重区间（WACC）、比率区间（合并 nci_ratio）、折现率 > 增长率（DCF Gordon）。
- ❌ 两处高 severity 不一致（F-01、F-02）与一处重复计数（F-03），详见汇总表——这是本次审计**必须修复**的核心项。

## 6. P0 修复建议示例（供直接落地）

**F-01** — 在 `financial_warning.py` 的 `calc_altman_z` 等函数中，将非有限值归一：
```python
# _compute_ratios 中 x4=inf 时，主函数返回 value=None：
if not math.isfinite(z):
    return ToolResult(
        method_id="MTH-02-004", method_name=...,
        value=None, inputs=..., details=x,
        warnings=r["warnings"] + ["Z 值为非有限（无负债主体），无法给出数值，建议定性判断。"],
        notes=...,
    )
return ToolResult(..., value=round(z, 4), ...)
```

**F-02** — 在 `tax_tools.py` 的 `tax_health_score` 增加白名单：
```python
_LEVELS = {"正常", "关注", "高风险", "不适用", None}
for name, level in (("增值税税负", vat_burden_level), ...):
    if level not in _LEVELS:
        raise ToolValidationError(f"{name} 取值应为 正常/关注/高风险/不适用，收到：{level!r}")
```
